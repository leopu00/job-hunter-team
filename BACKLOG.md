## 🔴 Pacing & budget correctness

- 🔴 **[PACING-RESET-EDGE-FREEZE]** — false emergency freeze from `proj>200` at the reset edge: `proj = usage / window-fraction` blows up as `reset_in→0` and the Sentinel skill has no exception, so it froze 7 healthy agents (2026-06-26). Fix: suppress the `proj>200` trigger when `reset_in≈0` in `agents/sentinella/_skills/emergency-handling/` (×7 languages) + `shared/skills/compute_metrics.py` (same guard drives `suggested_throttle_s`).
- 🔴 **[PACING-DAILY-HALT-STANDBY-LEAK]** — the daily hard-stop silences the bridges but not the agents: workers wake from throttle timers, ping the Captain, the Captain replies → ~1–2%/night leak. Fix: workers and Captain honor `daily-halt.flag` on wake; bridge re-ESCs any session that talks during halt. Detail: `docs/internal/postmortems/2026-07-02-daily-halt-standby-leak.md`.
- 🟡 **[PACING-PROJ-VOLATILE]** — bridge still gates some decisions on the volatile `proj` (g-spot wake, throttle ladder, coast). **Deliberately deferred** (live and working — do not touch casually); if reopened, move the gates to velocity-based signals. Analysis: `docs/internal/roadmap/2026-06-20-proj-volatile-pacing-todo.md`.
- ⬜ **[JHT-KIMI-OPTIMIZE]** *(M4)* — Kimi €40 tier out of beta: in-window variance analysis (buffer 88→92%), external multi-week beta runs (two live now), 1-month steady-state stress test.
- 🔴 **[COORD-STATUS-PUSH-TO-PULL]** — workers narrate their state to the Captain instead of letting him look it up, and every line wakes the most expensive model in the fleet. Measured on a first-run team 2026-07-27, ~1.5h of pane history: **37 inbound messages, of which 30 (81%) are pure status** — `DONE` 12, `START` 8, `INFO` 8, `ACK` 2 — against 3–6 that actually ask for a decision (`BLOCKED`, `REQ`, `MSG`). Each one costs a Captain turn, and under the automatic model split the Captain runs on Opus while Scout/Analyst/Scorer run on Sonnet: a Scorer's "done" wakes the priciest agent to do nothing. **The pull side already exists and is strictly better**: `db_query.py recent-activity` (already granted via `db-query`) returns per-agent counts plus every transition with timestamp, actor, position and reason — `#22 checked→scored`, `#27 new→excluded — [DEAD_LINK]` — in **one call** instead of 30 wake-ups. A `DONE` carries less information than the row it produced. Proposed shape: drop "notify the Captain when you start/finish" from the worker prompts, keep push **only** for what leaves no trace in the DB (`BLOCKED`, conflicts, decision requests), and add `recent-activity` to the Captain's heartbeat loop. ⚠️ The asymmetry is the point: `recent-activity` shows who *produces*, so a stalled agent **disappears** from it rather than standing out — which is exactly why blocked-state must stay push. Related: [JHT-SENTINELLA-OPTIMIZE], and the coordinator-burn work already done.
- 🔴 **[SCORE-INTEGRITY-NO-UPSTREAM-FILTER]** — nothing in the prompts protects the score from being inflated by upstream selection, and on 2026-07-27 only an agent's own judgement did. Asked to make Scouts "learn from the scores", the Captain issued two instructions: *prioritise what scores well* and *avoid what scores badly*. A Scout **refused the second one and demanded written confirmation**; the Captain agreed and withdrew it. The Scout's reasoning is the rule we should be encoding: if Scouts filter weak positions upstream, the Scorer grades blind, and the user reads the score as an objective measure, then **the scores inflate themselves** — the user sees a list full of 80s and concludes the market is rich in good matches, when in fact we chose what to show her. A number that *looks* objective, on which she decides where to apply. Damage had already started: another Scout had discarded a senior auditor on job title alone (recovered). **The distinction to hard-code**: search *priority* (where to start, given limited time) is legitimate and useful; exclusion *filtering* (what is allowed in) corrupts the measure. Only mechanical rejects belong upstream — out of area, hard requirement the profile cannot meet, dead link, duplicate. Grep confirms neither `agents/scout/` nor `agents/scorer/` states any of this today, so the guarantee rests on one agent objecting; the failure mode is silent, and its symptom — higher scores — reads as good news. Note the legitimate half of the request did land and is worth keeping: Analysts now separate legal from technical roles, estimate missing salary (20 points of 100, and the most frequently empty field), and flag real seniority.
- 🔴 **[MODEL-PIN-NEVER-PROMOTES]** — the `model-pin` step shipped and ran in production without promoting anything, though the newer model was fully available: it will **never** promote one as written. Two defects, both observed on a live box 2026-07-28. (a) **The probe false-negatives**: it reported `verifica INCONCLUSIVA (--quiet -p ok exit 1 — To resume this session: …)` while the same model answered by hand a minute later with exit 0 — and that `To resume this session` line prints on success too, so it must not be read as an error. (b) **Invalidating the pin is not enough**: the CLI rewrites it back to the *old* alias, because that is the plan default — after boot the file said `kimi-for-coding` again. What actually worked was writing the new alias explicitly, after which the agents came up as `agent (K3 ●)` with the context window going 262144 → 1048576. Fix: read the aliases the config already lists (`[models."…"]`), pick the best by **declared capability** — highest `max_context_size` within the same family, not by name — and **write** it. Note sessions read the pin at startup, so a manual run has no effect until they restart. Detail: [`docs/internal/roadmap/2026-07-28-ticket-provider-cli-autoupdate.md`](docs/internal/roadmap/2026-07-28-ticket-provider-cli-autoupdate.md) § FOLLOW-UP.
- 🔴 **[PROVIDER-CLI-AUTOUPDATE]** — the container must refresh the active provider's CLI on boot, before the team starts, instead of waiting for a human to run `jht providers update`. Spec, constraints and acceptance criteria: [`docs/internal/roadmap/2026-07-28-ticket-provider-cli-autoupdate.md`](docs/internal/roadmap/2026-07-28-ticket-provider-cli-autoupdate.md). Hook in `cli/src/commands/pid1.js` before the bridges; reuse `providers.js::handleUpdateInContainer()`. Non-negotiable: **fail-safe** (a failed update must never stop the container from starting), active provider only, **never changes the model** — a newer model is reported to the Captain as a finding, since it changes cost, behaviour and context window. Testable by deploying onto a box with a stale CLI and watching the boot.
- 🔴 **[PROVIDER-MODEL-DRIFT]** — nobody in the team is responsible for noticing that a newer model exists, so a box can run a generation behind indefinitely. Found 2026-07-28: a live VPS was running **K2.7** while its provider had shipped **K3 on 2026-07-17** — eleven days earlier — with 2.8T parameters, a **1M-token context window**, and benchmarks above the previous generation on coding and agentic tasks. The Maintainer owns *infrastructure* (container, VPS, dependencies, disk/RAM, browser/Playwright/runtimes) and its prompt says nothing about providers or models; the Doctor owns *agent health*. Neither watches versions, and `jht providers update <p>` only refreshes the CLI when someone runs it. Worth noting the CLI already accepts `--model`, but JHT never passes it — the model is whatever the account defaults to, so even an updated CLI may not move. **The context window makes this urgent, not cosmetic**: the same night, two agents stalled at 565k and 168k tokens against a 262k window (see [session notes](docs/sessions/2026-07-27-first-run-night-observations.md) §6) and had to be cleared by hand — a 1M window would have absorbed both. Fix worth scoping: give the Maintainer's daily sweep a provider-version check (installed CLI vs latest, active model vs available), reported to the Captain as a finding rather than auto-applied — switching model mid-run changes cost and behaviour, so it stays a user decision.
- 🔴 **[BURN-INTENT-OVERRIDE]** — spending automatisms fire on numbers alone and have **no way to know the user decided otherwise**, so an explicit "budget is not a constraint, go faster" cannot be honoured: each brake has to be dismantled by hand from outside, and one of them undid the change on its own. Observed 2026-07-27 — five successive derogations were needed and still fell short. `daily-halt.flag` is the clearest case: the three bridges write it when `spent > daily_budget + 5%` and ESC every session, without ever asking whether the user has requested the opposite; the coordinator then becomes unreachable while acting on an order given an hour earlier. Same shape without a flag file: `WORKER_FLOOR` (rewrites any lower value **on read**), the ladder, and `pace_guard` (**rewrites** the throttle each tick, so a manual override lasts under five minutes) — layered, so removing one does nothing while the next restores it, and every layer presents the identical symptom *"throttle is back to 300"*. **One brake lives in a prompt**: after six workers were exempted from the floor in code, the Captain **narrowed the exemption himself**, correctly citing C-02 (*"non esiste «porta il throttle a 0»"*) — so a technical derogation must also reach the agents or they revert it in good faith. What is needed is a single source of truth for user intent, read by every spending automatism **before** it blocks: removing the flag afterwards is too late, the team has already been ESC'd. It must expire on its own (nothing created that night deactivates itself), reach the Captain's context, and leave the **safety** brakes untouched — `weekly-halt` (the provider stops answering), `host_agent_cap` (RAM ceiling; exceeding it caused load 24 on 6 cores and *less* output), `SC-09` (upstream volume yields negative downstream throughput), `freeze_team`. Full inventory with readers/writers per flag: `docs/internal/roadmap/2026-07-28-burn-on-demand-gates.md`.
- 🔴 **[TEAM-STANDBY-ZERO-SPEND]** — **a running team spends whether or not it works, and nothing can bring that to zero.** Measured 2026-07-29: with all five workers at `throttle=3600s` and **zero positions produced**, weekly still climbed 98% → 100% in about an hour — roughly **2 weekly points per hour on a completely idle pipeline** — then hit the wall and froze the team for four and a half days until the provider's weekly reset. The residual spend is not the workers but the **core** roles (coordinator, assistant, sentinel, doctor, mentor) plus the three bridges, which keep exchanging ticks every 5-15 minutes regardless of whether there is work; none of them reads `config/throttle.json`, which governs workers only. **The two skills that look like they cover this do not**: `freeze_team.py` excludes `{CAPITANO, ASSISTENTE, SENTINELLA, SENTINELLA-WORKER}` and `soft_pause_team.py` excludes `{SENTINELLA, ASSISTENTE, SENTINELLA-WORKER}` — both pause exactly the operatives the throttle can already silence, so applying either during the incident would not have changed the outcome by one point. The exclusion is deliberate: the sentinel is what notices quota is back and sends `[RIPRENDI]`, so silencing it without a replacement leaves the team off forever. The unlock is that **reading quota costs no model turn** — bridges fetch it over HTTP/CLI — so a bridge can stay alive as the alarm clock provided it stops *writing* to tmux. Design principle: in standby the bridges keep **reading** and stop **talking**. Consequence worth stating plainly: below a certain output level the choice is not fast-vs-slow but **on-vs-off**, and today there is no middle. Full spec with wake-on conditions, flag ordering and acceptance tests: [`docs/internal/roadmap/2026-07-29-ticket-team-standby-zero-spend.md`](docs/internal/roadmap/2026-07-29-ticket-team-standby-zero-spend.md).
- ⬜ **[SPAWN-STAGGER-BY-PERIOD]** — spawn staggering exists (C-02: *"spawn staggered ~10min l'uno dall'altro"*) but the offset is a **fixed 10 minutes**, unrelated to the throttle period the workers will actually run on. With N workers sharing period T, the offset that spreads them evenly is **T/N**: three workers at 5 min want 1m40s apart, not 10 min. A fixed offset larger than T is the worst case — the first worker has already cycled twice before the second starts, so the phases land wherever they land. Note the complementary trap: waiting a **full T** between spawns puts them in permanent lockstep, since worker A's next cycle lands exactly on worker B's start. Pairs with the coprime ladder (shipped 2026-07-28): the ladder keeps workers on *different* rungs from resynchronising, the offset keeps workers on the *same* rung from starting together. The initial phase is all this sets — task duration varies enough that phases drift on their own. Touches `.launcher/start-agent.sh` and the `spawn-agent` skill.
- ⬜ **[SOURCE-YIELD-MEMORY]** — the team keeps no memory of how well a *source* performs, so a Scout can work an unproductive lane for hours and nobody notices. Measured by hand on a live team 2026-07-27 (50 positions): the dominant job board returned **62% reaching a score**, while two other lanes returned **0%** — one of them an aggregator that serves expired ads as HTTP 200 with the closed-marker buried in the page's localisation bundle, so the standard link gate cannot discriminate on it. Nothing in the system looks at this: the Mentor reads patterns but advises the *user* about skills, and the Captain assigns lanes by what is **uncovered**, not by what has **paid off**. Note the defence-in-depth worked exactly as designed — Analysts caught every dead link with `recheck-liveness` and the user saw none — so this is not a correctness bug; the cost is the wasted analyses upstream of that catch. **Deliberately not a blocklist**: sources are discovered by exploration, not hardcoded, so banning a domain ages out immediately — the same exploration produced the highest-scoring position of the run. What is missing is the aggregate: yield per source, surfaced where lanes get assigned. Constrained by [SCORE-INTEGRITY-NO-UPSTREAM-FILTER]: yield may reorder **where sourcing starts**, never what is allowed in. **Osservazione dell'utente 2026-07-28, da approfondire prima di implementare**: nel gioco non ha mai visto due Scout lavorare *insieme* — per esempio entrambi su LinkedIn, coordinandosi — e ritiene che sarebbe piu' efficiente della divisione per territori. Va notato che **C-21 prescrive l'opposto**: territori divisi (cerchie/fonti/citta'/fasce via `scout-coord`), e tratta "due Scout che scrapano la stessa fonte in parallelo" come il *sintomo* di un coordinamento fallito, da correggere ripartizionando o killando. Quindi non manca la funzione: divergono la regola scritta e l'aspettativa dell'utente. Due domande aperte, entrambe da rispondere prima di toccare il codice: (a) quale delle due configurazioni rende di piu' su una fonte grande e paginata — divisione per territorio o due agenti sulla stessa fonte con una divisione piu' fine (pagine, filtri, fasce orarie)? (b) perche' C-21 **non si vede all'opera**: e' il Capitano che non scala mai oltre 1 Scout, e' la skill `scout-coord` che non viene aperta, o la divisione avviene ma e' invisibile nell'ufficio? La (b) e' misurabile subito sui log di un team vivo e va fatta per prima: se la squadra coordinata non parte mai, ottimizzarne la strategia e' prematuro.
- ⬜ **[SCORE-FEEDBACK-LOOP]** — no mechanism feeds scoring outcomes back into sourcing. The Mentor already reads scores (`mentor-patterns`, read-only, threshold-gated) but speaks **to the user** — "this missing skill separates you from a third of the market" — and never reorients the Scouts. Asked for it live on 2026-07-27, the Captain had to improvise it as free-text instructions, which is exactly how it drifted into upstream filtering. If built, it must be constrained by [SCORE-INTEGRITY-NO-UPSTREAM-FILTER]: it may reorder *where sourcing starts*, never *what gets ingested*, and the Scorer must stay blind to it.

> `[STEPCAP-THROTTLE-RESUME]` (un agente che sbatte sul cap `max_steps=100` restava parcheggiato per sempre) è stato **chiuso per implementazione** il 2026-07-28. `.launcher/stepcap-watchdog.py`, avviato da pid1 accanto agli altri watchdog, guarda il **progresso** invece dell'esistenza: rileva, mette in **throttle**, e solo alla scadenza riprende. > `[CLOUDSYNC-PUSH-ONLY-WHEN-WATCHED]` (data reached the cloud only when a browser asked for it) è stato **chiuso per implementazione** il 2026-07-28. ## 🖥️ Applicazione nativa Godot

- 🔴 **[GAME-VPS-SSH-USER]** — "Collega VPS" hard-codes `root@`, so it can only talk to providers that hand out root. Found live on 2026-07-27 connecting a new box on OVHcloud: `SSH non disponibile: root@<ip>: Permission denied (publickey)` — OVH logs you in as `ubuntu`, and it is not an outlier (AWS gives `ubuntu`/`ec2-user`, GCP and Azure the account name; Hetzner's root-by-default is the exception). Fix: an **SSH user** field next to the IP, default `root`, threaded through the seven call sites in `game/scripts/setup/setup_service.gd` (`1153`, `2092`, `2101`, `2132`, `2406`, `2459`, `2674`) and persisted with the rest of the VPS config. Workaround used to unblock the test: install the key for root on the box too.
- 🔴 **[GAME-VPS-FINGERPRINT-STALE]** — the fingerprint shown under the key field is not recomputed when you pick a different key: with a per-box key selected the panel still displayed the fleet key's fingerprint (2026-07-27). That field exists to be compared against the fingerprint the provider shows, so a stale value doesn't just mislead — it turns the anti-MITM check into false assurance. Fix: recompute on key change in `game/scripts/setup/setup_service.gd:1240-1249` / re-read `key_info` in `game/scripts/ui/section_panel.gd:2769`.
- 🔴 **[GAME-SETUP-CHECKLIST-READS-LOCAL]** — the "Attiva team" checklist grades the **local machine** while connected to a VPS, so it can both block a fully configured box and green-light someone else's data. Measured 2026-07-27 against a freshly provisioned box: step 02 *Provider* was red with "manca l'abbonamento" although that box had a declared plan in its config — `_declared_plan()` (`game/scripts/setup/setup_service.gd:467`) reads the laptop's `~/.jht/jht.config.json`, where `plan` is null. Worse, step 03 *Profilo* went **green while validating a different tester's profile**, left over in the operator's local `~/.jht/profile/`, instead of the connected box's; step 04 likewise passed on local working hours rather than the remote ones. Only step 01 (the connection itself) is genuinely remote. Consequence: a correctly provisioned VPS can never reach 4/4, so `ready` stays false and the activation gate never opens; conversely the checklist can certify a profile that belongs to someone else entirely. Fix: route every probe behind the same transport as step 01 (`_run_ssh`) when a VPS is connected, and never fall back to local paths silently — an unreadable remote value must render as unknown, not as the local one.
- 🔴 **[GAME-MAP-DROPS-ADDRESS-AND-PRECISION]** — the office map plots pins but throws away both the street address and the confidence behind it. The VPS query (`game/scripts/backend/vps_backend.gd:161`) selects `p.office_lat, p.office_lon` and **neither `p.office_address` nor `p.office_verified`** — `office_address` appears in **no** `.gd` file at all. Two consequences, measured on a live box 2026-07-27 (30 geocoded positions, 30 with a full street address, 23 flagged verified): (a) the exact address the Analysts worked to obtain — street, number, postcode — **cannot be displayed anywhere in the office**, because the client never fetches it; (b) with `office_verified` missing, a pin resolved to a street number and one resolved to the city centroid render identically. The visible symptom is a cluster: 30 geocoded positions collapse to **24 distinct coordinates**, because every unverified row shares the city centroid, so ~7 markers stack on the exact same point and read as a broken map. Fix: add both columns to the select, show the address in the position card, and treat `office_verified=0` as a distinct class — the existing `resolveCityPins` grid handles rows with *no* location, but not rows that have a city and lack a street, which is a different and more common case.
- 🔴 **[GAME-VPS-SWITCH-STALE-PIPELINE]** — switching the connected VPS does not invalidate `BackendBus.pipeline_counts()`, so the office keeps drawing the **previous** machine's pipeline. Measured 2026-07-27 while connected to a newly provisioned box: the Scorer desk showed a 692→697 paper pile against 14 positions in that box's DB — the number tracked the previously connected box's 694 `scored` rows, drifting live as *that* team worked. ## 🛠️ Infra & CLI

- 🔴 **[JHT-CLI-AGENT-PARITY]** — **the CLI reads and commands, but cannot decide.** The project's stated design rule lives in `docs/guides/AI-AGENT-INTEGRATION.md`: *"If a feature requires opening the web dashboard or the Desktop app to be configured after install, that's a bug — one CLI surface for humans, AI agents and the Desktop launcher."* Measured against the game's `BackendBus` verbs on **2026-07-25**, it is not being met.

  | | 🎮 game | 🔧 CLI |
  |---|---|---|
  | read — positions, state, stats, logs, graphs | ✅ | ✅ `positions list/show`, `stats`, `status`, `logs`, `sentinella graph` |
  | command — start/stop the team, talk to an agent, providers, hours | ✅ | ✅ `team start/stop/send/chat`, `providers`, `working-hours`, `cron` |
  | **decide** — judge a position, exclude it, request a CV, open a ticket, post a standing directive, save the profile, fetch a produced artifact | ✅ | ❌ **nothing** |

  `jht positions` describes itself in code as *"Query DB posizioni (proxy a db_query.py)"* — read-only by construction. The missing verbs are exactly the ones that carry a **user judgement**, which is what the human does in the office and an agent currently cannot do at all.

  The capability is already there, one layer down: `shared/skills/{ticket,team_directives,write_request,feedback_query}.py`. What is missing is the `jht` verb in front — wrapping, not design.

  **The bigger blocker is not the verbs, it is the output format.** Only **3 of 37** command modules support `--json`/`--format` (`container`, `profile`, `tools`). An agent reading `jht positions list` gets an ASCII table meant for a human eye and has to parse it with brittle regexes — while `db_query.py` underneath already knows how to emit JSON and the flag simply is not exposed. Work, in order: (1) `--json` across the read commands; (2) the decision verbs; (3) a CI parity check that fails when the game gains a verb the CLI lacks, so this cannot drift again.

  **Done 2026-07-25 — all three steps.** (1) `--json` on the seven `db_query.py` read commands, surfaced on `jht positions list/show/dashboard`. (2) Decision verbs: `jht positions exclude/restore/request-cv`, `jht ticket open/list/count/show/for-position/assign/resolve`, `jht directives add/list/edit/archive/show`. Two skills had to be written or extended, because the verb existed *only* inside a web route and was therefore browser-only: `shared/skills/user_exclude.py` (new) and `ticket.py open`. (3) `tests/test_cli_game_parity.py` classifies every public `BackendBus` verb as covered / known-gap / not-applicable and **fails on an unclassified one** — verified by injecting a fake verb and watching it name it.

  **Residual, still open:** like/dislike/star feedback (lives only in Supabase `position_feedback`, needs the cloud lane, not SQLite), `fetch_artifact`, `upload_user_document`, and read/write of the coordinator settings. Each is listed in `KNOWN_GAPS` inside the parity test, so the list cannot quietly rot. Also open: `user_exclude.py` and the TS route now hold **two implementations of the same rules** — one test compares their reason sets, nothing compares their behaviour.
